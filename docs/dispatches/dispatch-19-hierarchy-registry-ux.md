# Dispatch 19 — Integrated hierarchy registry UX

## Owner direction and scope

October 22, 2026: the owner confirmed Territory means the existing **Region**. The intended model is Region → District → Store, with the DM owned by the District. The separate large handover form in Dispatch 18 was functional but felt disconnected and cluttered.

This change refines the existing UI and uses the same reviewed server commit, membership checks, audit and concurrency protections. It does not introduce another hierarchy level, rename IDs, alter API fields/scopes, change employment or accounts, or migrate live assignments. Karlo remains untouched for testing. Test-affected data must not be automatically repaired or restored.

## User experience

- Browse existing Regions and Districts first, with names prominent and IDs secondary.
- Filter Districts by Region; unavailable/retired records remain visible for review.
- Open creation forms only when needed. Existing versioned metadata editing and conflict review remain available.
- Each District shows its DM or explicit vacancy, retail-store count, and whether District ownership still needs setup.
- Open manager settings from that District. There is no second District selector or global leadership panel.
- Preserve the impact preview, reason, explicit acknowledgement and atomic confirmation. Disable competing registry actions during leadership editing and saving. A failed/uncertain save still requires checking saved state before rebuilding a preview, not blind retry.
- In retail store editing, DM is read-only even for legacy Districts. Region filters the available Districts; managed Districts immediately supply the inherited DM. Legacy Districts show a setup warning and preserve their prior store assignment until reviewed. Non-retail direct leadership remains outside this retail change.

## Transition boundary

This is not a blanket data cutover: omitted District `districtManagerId` still means legacy ownership to existing server/import clients; explicit null means a District-owned vacancy. New District creation still requires subsequent explicit manager/vacancy setup through the reviewed workflow. The UI must not describe legacy assignments as inherited or fabricate a vacancy/manager. The unchanged server enforces District ownership after setup. Removing legacy server/API/import compatibility and making all creation flows District-owned requires a separate validated migration; hiding the store picker is not that migration.

Regional Manager ownership, controlled position eligibility, full offboarding, correction workflows and operating-status work remain in the broader plan. Historical API snapshots retain their recorded assignments. No authenticated production API acceptance is claimed by synthetic UI tests.
