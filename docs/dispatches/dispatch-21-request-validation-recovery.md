## Recovery

- A new form uses a UUID request ID and retains the exact submission envelope in this account's tab session storage **before** sending. If storage cannot be used, submission fails before network dispatch. An uncertain result locks its original content; reopening/reloading the tab's form recovers that envelope. No blind new-operation retry occurs.
- The server stores a canonical JSON digest and authenticated actor binding on the retained request. An exact single-submission replay returns its current saved state, including a later Approved/Rejected decision, without another write/audit/notification or reopening. Changed content/another actor cannot reuse the ID. This is not a generic idempotency guarantee for arbitrary batched commits.
- Recovery offers retry of the same operation or **check saved state / cancel if not saved**. If saved, reconcile it without cancelling/reopening. If absent, a transaction creates a durable cancellation seal in `request_submission_receipts` and audit. Every pending-request commit checks that seal, including batched writes, so late arrivals cannot save after cancellation. Repeated cancellation is safe; content/actor mismatch fails closed. Only confirmed cancellation unlocks an editable restored draft with a new identity on replacement.
- Session storage is scoped to the account and current tab; it is not a cross-device, closed-browser or disaster backup. No token is stored. Do not clear uncertain operations blindly. Closing the recovery dialog retains it; use Submit New Request in the same tab to resume. Corrupt recovery storage fails closed for administrator investigation.
- Submission notification remains post-commit and best-effort. Replayed submissions deliberately do not send again; a response lost before original client notification may leave mail unsent. No durable mail-delivery guarantee or real inbox acceptance is claimed by this work.

## Release safeguards and next sequence

Cancellation seals and actor-bound replay are write-contract changes. A rollback to PR #30 lacks them: prefer forward repair, or restrict request submissions/reviews and reconcile in-flight operations before any older writer serves. Traffic rollback is not request/target/receipt recovery. Do not delete request history or cancellation receipts as cleanup; retention policy is separate. District ownership guards and pre-ownership rollback restrictions still apply.

Next: shared time-zone-aware operating-state resolver and narrow immediate closure/renew/reopen commands, then address/suite/wayfinding corrections and consistent approved consumer/export surfaces. Emergency actions must authorize from canonical Person assignments and current server accounts, not free-text titles or broad UI filters. No public v1/v2 field semantics may change silently; time-driven expiry requires a separate explicit current-state read or versioned projection. Data restoration and private consumer acceptance remain independently gated.
