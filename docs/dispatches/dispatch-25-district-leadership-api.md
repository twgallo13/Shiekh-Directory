## Contract and safety

- New `/api/v3/snapshot`, `/api/v3/district-leadership` and `/api/v3/location-districts`, with exact-document-ID detail routes. Both datasets use the same immutable 15-minute Firestore read time, client/token/grant binding and dataset/page-size-bound cursor. Read all pages of both datasets before consumer reconciliation; failures/expiry are never empty successful data.
- New `district-leadership:read` returns canonical District-owned DM identity/name/lifecycle, Region context and minimal store membership. It includes zero-store and retired Districts. Absent ownership, explicit null vacancy, invalid reference and missing Person are distinct. Never infer an owner from copied Location DM fields or descriptive titles; non-retail/unclassified/applicability conflicts stay explicit.
- `district-leadership:contacts:read` requires the base leadership grant. Existing `locations:read`, `personnel:read`, `staffing:read` do not imply either new grant; existing v1/v2 serializers and persisted-assignment semantics stay frozen. For DM-only needs, the two new minimal grants replace the need for broader v2 staffing access. Keep existing location access if the consumer still needs v1 store fields; do not claim independently timed v1 and v3 reads are one atomic snapshot.
- Contact reads use only canonical Person `workEmail`, never legacy `email`, User/Firebase fields, personal aliases, phones, custom fields or store-inbox substitution. Clearly Active lifecycle, valid address and current company domains `shiekhshoes.com`/`shiekhshoes.org` are required. Missing/invalid/unapproved-domain/inactive/ambiguous/missing-person and known shared-inbox contacts are null with a reason. Domain policy changes require review; no verified sign-in claim is made. The shared-inbox scan checks only that public field on all Locations at the same pin, case-insensitively, bounded at 1,000 documents. Larger/incomplete reads fail closed, not partial safety success. This cannot certify mailbox uniqueness or fix misclassified source data.
- All output is allowlisted and no-store. Source queries are field-masked and bounded (100 page records, 300 references, 100 reference documents per read); no account data is fetched. Logs omit tokens, snapshots/cursors, raw errors and contacts. Existing client tokens are not rotated when grants change, but snapshot grant digests invalidate old runs immediately.
- Existing administrator-only Settings → Directory API grant review gains explicit new choices/dependency validation plus clickable served guide/OpenAPI. No default new grant and no live mutation is performed by adding the controls. Exact-client production grant/contact exposure requires owner approval at action time. Credentials remain server-side; client summaries never expose token secrets.

## Handoff, documentation and rollback

The maintained guide and strict allowlist are [district-leadership-api.md](../district-leadership-api.md) and [district-leadership-openapi.json](../district-leadership-openapi.json). They are copied to deployed documentation endpoints by the build and linked from Settings. API.md/schema/consumer blueprint distinguish this from v1/v2; v2 guide links the separate contract. A schema is not proof of deployment or live permissions.

Prefer forward repair. Removing the new scope catalog in an older-code rollback causes newly granted clients to fail scope parsing, potentially including their old location access. Record/revert only explicitly authorized new grants before such a rollback, using exact expected-grant concurrency checks and preserving old tokens/grants; coordinate consumer restart. Never restore old client documents or rotate/revoke a token blindly. Traffic rollback does not undo grant changes. If no new grant has been issued, older code remains compatible with unchanged old client documents. Preserve stable District/Person/Location IDs and later legitimate writes.
