## Implemented boundary

- [Intent normalizer](../../server/personTransitionIntent.ts): fixed schema, explicit final controlled positions/lifecycle/reason, responsibility and workplace decisions, exact Pending acknowledgments; rejects unknown keys, duplicate owners/IDs, coerced fields, arbitrary paths/writes and oversized bodies. Position/support/acknowledgment sets normalize; leadership array order remains meaningful.
- [Pure planner](../../server/personTransitionPlanner.ts): complete bounded detached snapshot contract, unique document IDs, strict consumed field shapes, explicit exact-read Person absence, native update-time metadata and omitted/null/zero version distinction. Computes server-internal field patches, District-owned retail derived copies, Location-owned responsibility changes, final-role eligibility, all-state linked-User inactivation blockers, workplace constraints, exact-ID Pending review and historical-copy warnings. No title/email fallback for new assignments, ownership adoption or unrelated occupied-slot displacement.
- District changes include retired member stores and zero-store Districts. Retired subject-owned District vacancy may proceed without repairing an inactive/missing parent; replacement/new responsibility still requires valid Active territory. Multiple explicit positions do not implicitly assign a District. Location phone/name compatibility copies use the existing phone resolver; outgoing SM contact is cleared, replacement privacy is not widened by default. Unrelated array IDs/names/order and source fields remain untouched.
- `review` is contact-redacted; internal patches/preconditions are **server-only**, contain source/contact data and must never be serialized as an HTTP response. Reason/request prose/account email/Firebase UID/phone are absent from review. Pending requests remain unchanged and do not become inactivation blockers after acknowledgment. Workplace/support links remain separate from management/mailbox authority.
- Deterministic domain-separated intent/state/plan hashes bind complete supplied inventories, exact absences, source content/native times and membership, including unversioned edits. Changing only adapter read ID or inventory ordering does not change the plan. No signature, expiry, authorization, query-lock or coherent-read guarantee is created by hashing. `ready` means local consistency only, never permission to commit.
- More than 90 unique changed business documents, conservative business estimates over 4 MiB or audit estimates at/above 900,000 bytes block the whole plan. Multiple effects merge into one patch per document. Blocked results contain no internal mutation list. Estimates deliberately overcount source+patch content; SDK/platform limits remain authoritative.

The adapter must supply a single actual coherent, complete read with limit+1 overflow detection and narrowly projected exact People reads. The pure function cannot authenticate that assertion or detect omitted documents from a fabricated snapshot. It imposes an additional defensive 5,000 exact-People ceiling and 8 MiB JSON snapshot cap; these do not expand inventory/provider limits. It neither increments versions nor emits audit/receipts: future writer must do those once per unique document and revalidate current authority/predicates/preconditions atomically.
