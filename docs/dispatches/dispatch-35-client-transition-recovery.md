## Delivered

`src/lib/personTransitionRecovery.ts` provides an unwired browser adapter and pure reconciliation helpers:

- Minimal marker schema (version, UUID v4, Person ID, command digest) and browser SHA-256 derivation matching the server's normalized-intent/envelope identity. Derivation is not signature verification, preview approval, authentication or submission admission. No raw intent, token, change reason, contacts, names or account-role cache is persisted.
- Durable localStorage keys use the existing protected `shiekh_` prefix plus a hashed actor namespace and operation UUID. Each read/write checks a supplied current authorized Active Company-wide administrator session with matching user/account UID. A previously opened vault rejects another actor or a denied/signed-out session; delayed lock/crypto/refresh completion rechecks the session before proceeding.
- Required Web Locks serialize writes across tabs; no unsafe lockless fallback. Writes have read-back confirmation; malformed records, missing crypto/locks, storage failures, ID/content reuse and more than 50 own markers fail closed. No marker is evicted because of preview expiry. Multiple already-unresolved operations for one Person are preserved for reconciliation, not silently discarded.
- Strict fixed-schema outcome/list parsers match the backend's minimal responses. Unknown/private fields, mismatched command identity, invalid dates/outcomes, duplicate changes/operations, incomplete/overflow lists or contradictory immutable times fail closed.
- Reconciliation combines all local markers, their exact status responses and the complete own-prepared list. Missing/unknown/prepared remains unresolved; server-only preparations are inspect/cancel recovery context, not a reconstructed editable intent. A matching terminal status wins over an older prepared-list snapshot. The plan always reports `canSubmit: false`; no network or submission is performed.
- Resolution removes only a matching marker after confirmed cancellation, or after a committed outcome **and a successful refresh of saved Directory state**. Failed refresh, permission/session loss or unconfirmed outcome retains the marker. It never merges receipt versions over newer Directory data.

## Boundaries / integration still required

The module is not imported by the app or AuthProvider. There is no live controller, Firebase observer/session-generation integration, API transport, automatic startup/sign-out reconciliation, prepare/commit dispatch or new dialog. Explicit sign-out's existing `clearProtectedStorage` already removes this prefix; tests prove compatibility, **not completed automatic authentication-boundary wiring**. Implicit sign-out/direct actor-switch cleanup and cross-tab auth-generation fencing must be integrated and tested before enabling submission. Permission loss must retain an inaccessible unresolved marker until authorized reconciliation or explicit sign-out; do not treat it as cancellation.

This is app-level namespace/session isolation, **not at-rest encryption, a sandbox against same-origin script/XSS, or server authorization**. The vault requires a trusted monotonic session-generation provider and checks it before/after asynchronous work, fencing stale work even when the same UID signs back in. The future AuthProvider/controller must advance it on authentication boundaries; the helper does not implement that observer. Future callers must use the trusted current session, reconcile before offering a new operation, preserve in-memory immutable intent/envelope only for the original operation, and fence all requests. Web Locks protect storage updates, not exclusive staffing ownership or cross-tab submission. The future server's fresh authoritative transaction remains decisive.

No live API call, browser/staffing/account/contact mutation, key/IAM change, client token/grant change or data restore was performed. Browser tests use isolated blank local pages, synthetic identities and no app/Firebase bootstrap. No visual acceptance is requested yet.
