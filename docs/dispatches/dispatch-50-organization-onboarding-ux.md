## User experience

New DM/RM profiles can continue after a **confirmed** profile save into Responsibilities → Review when the server admits new commands. Capability discovery failure/disabled configuration never turns that profile save into an error or repeats creation. Existing profiles have a capability-gated Responsibilities action; the registry has a corresponding management entry point and suppresses the older District-only handover button when the new catalog is admitted.

The current-responsibilities summary resolves canonical unit memberships and visibly labels Primary/Additional, including retained unresolved People. No unit is preselected. Selecting a unit for the current eligible Person preserves the incumbent Primary and proposes Additional coverage. A first manager/vacant unit needs an explicit Primary choice. All selected positions remain separate from workplace, store leadership, contact and sign-in permissions. Workplace stays optional; Corporate Office remains an existing valid choice.

The editor supports up to five namespaced units, includes current roster members, limits new manager choices to controlled eligibility, requires explicit reviewed legacy setup, and explains vacancies/removals/Primary changes before confirmation. No Primary is inferred from row order or removal. After refreshed source changes, draft reapplication is explicit: it applies the original intended add/end delta to current membership while preserving unrelated concurrent additions and the fresh incumbent unless a Primary change was explicitly proposed. A missing replacement leaves an unset Primary for review. Current-state/version checks still happen on the server.

Primary/Additional labels, compact cards, focus/error feedback, keyboard-accessible controls and a persistent action footer are used on desktop/mobile. Submitted-but-unconfirmed reviews expose Check status / Cancel review rather than another save. Confirmed success appears only after terminal proof and a strict saved-Directory refresh. The existing `refreshOperatingDirectory` swallows refresh failures; this workflow deliberately uses the stricter `refreshTransitionDirectory` boundary through an authenticated bootstrap read before forgetting a committed marker.

## Browser safety and recovery

- Exact bounded response parsers reject wrong operation identities, memberships, Primary choice, unit namespace, reason, unknown response fields and contact-enriched catalogs. Transport uses fixed same-origin routes, no-store, redirect rejection, deadlines, synchronous auth-generation checks and no automatic retry.
- A Web Locks actor lease prevents a second tab overwriting the first review marker. Stable versions/native transactions still resolve competing actors/devices; the browser lease is not authority.
- A marker containing only schema version and operation ID is verified in local storage **before** a preparation request. Names, contact information, reason, intent, review hash and credentials are not persisted there. Malformed/existing markers are retained rather than overwritten. Routine cache cleanup preserves this namespace; explicit sign-out still clears protected storage. Server-owned pending metadata supports later same-actor recovery.
- A missing receipt is not treated as terminal absence: cancellation seals the original ID before another submission. Committed confirmation must have the expected actor/operation audit digest; fresh saved records must apply successfully before marker removal. Failed refresh retains a known committed marker and retries recovery, never a second commit. Auth loss disposes the transport/lease, clears displayed protected data and fences late callbacks.
