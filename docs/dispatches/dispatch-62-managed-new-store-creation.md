# Dispatch62 — Managed new-store creation

New retail stores can prepare both canonical District and Regional Primary manager copies through the existing authorized creation path. Source implementation and isolated acceptance only; no production activation, data or deployment changes.

## Creation behavior

`prepareNewLocationLeadership` preserves Store → District ID → Region ID and independently respects each unit’s ownership. Existing District inheritance remains available for legacy Regions. Managed units require the supported model, explicit pointer/vacancy, active matching hierarchy and one clearly Active eligible Person with the controlled position. Explicit null Primary clears copied ID/name; legacy Region assignments remain separate. Non-retail Locations are not swept into retail inheritance. Unknown models, missing pointers, ambiguous/ineligible/inactive People and parent conflicts stop draft preparation before a request. Server transaction/roster validation remains the authority; no bypass flag was added.

The full create editor permits choosing Region/District while showing managed RM as inherited/read-only. Existing store editing stays separate. Non-retail RM fields are not falsely locked to a retail Region. Both create paths use explicit create-only version preconditions; a created record cannot be overwritten by repeating a create. A complete exact identity/version response with the expected hierarchy/manager IDs is required before applying a new Location projection or reporting success. This reuses existing atomic manifest confirmation, without adding a new receipt or recovery API.

Quick Add now awaits persistence. Rejected saves retain the form, values and visible error; fields/closure are protected while saving. Confirmed records enter context from the server response instead of an optimistic insert. The form requires actual street/city/state/ZIP and no longer substitutes `100 Main St`, Los Angeles or a made-up ZIP. It includes State/ZIP fields, accessible control names and a manager summary. Region/District and address fields stack on small screens. It preserves store-number leading zeros and does not grant accounts or mailbox access.

## Limits and continuation

Creation still uses the existing generic commit API. This milestone does **not** claim durable actor-scoped recovery for an unknown creation outcome: an interrupted reply must be reconciled before another creation attempt, and Quick Add’s complete interrupted/reopen recovery remains a release gap. Full editor retains its create identity in the open component; create-only collision and unique Store Number protect saved data, but are not a receipt/seal protocol. No automatic retry or rollback is added here.

Continue that creation recovery gap, linked type/retirement/delete support/diagnostics, correction and import preview/approval alignment, wider concurrency/consumer compatibility, independent exact-source review, bounded activation manifest, migration/rollback and guarded release/provider/browser acceptance. All activation/security/access/signing/runtime/release gates stay in place.
