# Dispatch 75 — Reviewed location use and removal screens

## Delivered source

Administrators can open **Location use & removal** from Locations or Regions & Districts. This is a separate workflow from ordinary contact, hours, retail-format and retirement edits. It uses the lifecycle capabilities, strict transport and recovery controller from Dispatches73–74. Disabled features and unauthorized accounts have no active entry point; paused commands retain recovery. No new public API shape, permission, credential or access grant is introduced.

The form requires an explicit Location, opposite retail/non-retail type, bounded reason, and a managed Region/District destination when becoming retail. Region changes clear District. Expected Location/unit versions come from fresh saved records. Local staffing release and API-removal acknowledgment start unselected. Unknown/future Location models fail closed. Removal eligibility is explained by read-only server preview, rather than hiding active or linked Locations and leaving administrators guessing.

Blocked previews show dependency blockers, affected People/workplace links, store account links, pending-request counts, coverage and server warnings without creating a preparation receipt. A ready review shows current/proposed type, canonical Region/District and inherited DM/RM, store assignments ending, linked records and coverage. Removal explicitly warns that the Location leaves Directory/API results, its ID stays reserved, history remains, and external app records are not automatically deleted or reassigned. The final confirmation uses the frozen server-prepared intent.

Forms do not persist staff/Location drafts or contact details. Close/discard explains that choices are not kept; original unfinished receipts remain recoverable. Back cancels the prepared review and refreshes saved state before an explicit retained-choice acknowledgment enables a new review. Server-only pending-review cancellation returns to a clean form without claiming a retained draft. Unknown outcomes, failed refreshes, session changes and mount cancellation use the existing controller safeguards. A concurrent window receives useful close/reopen guidance. Busy writes cannot be dismissed through the outer close control.

The modal follows the existing accessible dialog/focus/footer primitives. Current/proposed summaries stack on narrow screens, text can wrap, and confirmation actions remain in the fixed footer. Entry points avoid adding another nested modal to an unsaved Location editor.
