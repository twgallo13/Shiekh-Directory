Owner UX clarification, October 23: follow the [simple positions/assignments rules](positions-and-assignments-rules.md). Routine position additions stay ordinary Person edits, with separate District/Store assignment. Reuse this guarded command foundation for consequential removal/replacement/vacancy; a mandatory all-purpose promotion wizard is not the intended UX. Data restore remains deferred. This clarification does not relax atomicity, authority or recovery requirements below.

## 1. Business outcome and explicit limits

Source-only progress: [Dispatch 35](../dispatches/dispatch-35-client-transition-recovery.md) supplies unimported client marker storage and reconciliation helpers, not completed session/transport integration or an enabled workflow. Its real-browser storage tests do not replace the actual SDK concurrency/writer/end-to-end gates below.

An authorized administrator will deliberately review one Person's final controlled positions, current responsibilities, replacement/vacancy decisions and workplace/support links, then confirm one bounded atomic Directory change. Adding DM does not remove SM; retained multiple positions must be explicitly selected. A position does not assign a District or grant access. Descriptive title/department/contact fields are not rewritten to match a promotion.

V1 supports assignment/position changes and optional Person inactivation, not deletion or complete offboarding. It never changes Users, Firebase, API clients/tokens/grants, mailbox/provider permissions, private Notion or consumer applications. **Any linked Directory User, including Suspended/Revoked/unknown state, blocks Person inactivation until separately authorized account review/unlinking is completed.** Position-only changes may preserve existing links unchanged. Never tell the user that external access is revoked or that a departure is fully complete.

Region-owned/acting/date-effective leadership, store-level inherited-DM overrides, ownership migration, data restoration, occupied new-slot displacement and automatic notifications are excluded. Existing independently reviewed tools remain available; exclusion is not authorization to perform a real change elsewhere. Synthetic examples/tests only until the owner supplies concrete staffing selections.

## 2. Authority and source ownership

- V1 command preview/prepare/commit/status/cancel/recovery-list: unique current Active **Company-wide System Administrator**, reauthenticated on every request and rechecked transactionally. Preserve existing administrator-only District/account authority. The existing PR49 read-only review remains available to company-wide stewards; this does not give stewards the new writer. No consumer token, title, email, client role or review token authorizes a command.
- District-owned retail DM is changed at the District; all affected retail member copies, including retired stores, appear as derived effects. Omitted District ownership is legacy, not vacancy: do not adopt it automatically. New District assignment requires an already managed, Active District with explicit `null` owner and Active parent Region.
- Location-owned SM/AM/key-holder and existing legacy/non-retail DM/RM slots remain Location-owned until their separately reviewed migration. Retail District-owned DM is never a Location input. Regions supply hierarchy context, not an invented Region writer.
- A subject-owned retired District can be explicitly vacated, with all reviewed derived effects, without reactivating it or assigning a replacement. Preserve its status/parent; a missing/inactive parent is visible, not silently repaired. New/replacement assignment to retired or invalid-parent territory is blocked. Tests must distinguish removal-only cleanup from granting new responsibility.
- Historical copied DM references differing from authoritative District ownership remain warnings, not independent management slots. Do not clean up unrelated historical copies or reinterpret them as current responsibility. Preserve historical audit/request attribution.
- New/replacement leaders must be uniquely identified by canonical Person ID, clearly Active and explicitly mapped to the required controlled position. Unmapped/invalid eligibility requires separate deliberate mapping; no title/email fallback for a new assignment. Retaining untouched legacy links does not silently map them, but incompatible retained responsibilities block removing their required position.

## 3. Proposed intent (not arbitrary document writes)

Internal routes below are unavailable in production until implementation/configuration/release. Only `/preview` is implemented in the current source slice; all remaining routes are still absent:

- `POST /api/directory/person-transitions/preview`
- `POST /api/directory/person-transitions/prepare`
- `POST /api/directory/person-transitions/commit`
- `POST /api/directory/person-transitions/status`
- `POST /api/directory/person-transitions/cancel`
- `GET /api/directory/person-transitions/operations` (own unresolved preparations only)

Preview accepts `schemaVersion: 1`, `personId`, explicit final `positionIds`, lifecycle choice `keep` or `inactive`, a required bounded reason, responsibility decisions and workplace/support decisions. Reject unknown keys, duplicate owners/fields/IDs, unsupported actions, impossible role combinations and unchanged intent. Canonicalize semantic sets for hashing, but preserve order where AM/key-holder slot order is meaningful. Proposed request-body cap: 128 KiB; reason 1–1,000 trimmed characters; IDs use the existing canonical ID contract. These are application limits, not Firestore platform limits.

Responsibility decisions identify owner kind/ID and a fixed allowed leadership field, never a caller-supplied path. Every current authoritative responsibility of the subject requires an explicit `retain`, `vacate` or `replace` decision. Replace names exactly one eligible Person ID. For array fields, remove/replace only the subject's occurrence and preserve all other members/order; reject duplicate resulting members. Do not let this flow remove/reorder unrelated staff.

An explicit new assignment adds the subject only to a vacant scalar slot or appends to an array with no duplicate subject. Replacing an occupied unrelated slot is excluded from v1 and visibly blocked, not silently treated as vacancy. A promotion can retain SM and add DM without a new assignment; the confirmation must say it has not assigned a District.

Workplace/support decisions explicitly retain, clear or replace canonical links. They are not management or mailbox ownership. Missing/retired links remain visible; retaining untouched legacy links preserves them, while new links must pass current relationship validators. Inactivation does not require inventing a replacement workplace, and does not turn these context links into new server blockers.

Pending proposals/baselines remain unchanged review context, not new inactivation blockers. Show exact-ID matching requests and require acknowledgment of the review, without implying approval or silently rejecting/retargeting them. Their later approval must still satisfy current request/leadership/lifecycle guards. Expired/unknown/legacy relationships requiring a policy decision stop the affected intent instead of guessing.

## 4. Server-derived command preview

Do not submit PR49's informational digest as a command capability. A distinct planner reads a coherent bounded snapshot, validates every projected authority field, resolves subject/replacement eligibility and derives the entire mutation plan itself. Never accept caller-generated `DirectoryWrite[]`, copied names, before-state, versions or claimed membership as authority.

Reuse PR49's inventory limits initially: 1,000 Locations, 500 Districts, 100 Regions, 5,000 Users and 1,000 Pending requests, plus exact subject/counterparty Person reads. Require complete query results (limit+1 overflow detection), explicit absence, and native Firestore document update times as well as presence-aware application versions. Omitted, `null` and numeric zero are distinct preconditions. Missing documents/unknown states are not silently filled from bootstrap/browser data.

Return only a minimal review projection: subject's controlled-position/lifecycle before/after; each authoritative slot before/after and provenance; inherited-copy effects; retained/changed workplace links; minimal linked-account blockers; Pending request IDs/reasons; warnings; counts; expiry; explicit excluded external-access tasks. Counterparty contact fields, free-text request prose, account email/Firebase UID and raw document payloads are excluded. Source IDs/update times/digests do not grant access.

Before offering confirmation, require no unresolved blocking condition and a deterministic plan within all v1 limits: **90 unique business documents**, one receipt and one append-only audit; at most **4 MiB** conservative serialized business-write estimate; audit below the existing **900,000-byte conservative estimate**. Count a Location touched by several effects once, then version it once. SDK/platform limits and failures remain authoritative; estimates are not a platform guarantee. No automatic chunking, partial completion or arbitrary limit increase. Oversize work needs a separately reviewed bounded-batch/recovery design.

## 5. Review binding and freshness

The future read-only command preview returns a server-signed, domain-separated review envelope with a key ID, command audience/schema, actor UID, subject ID, normalized intent hash, authoritative plan/precondition hash, server issue time and five-minute expiry. It contains no raw contacts, private prose or proposed raw documents. An unchanged intent/state produces the same plan hash, though token issue time/signature may differ. The token is **not** authentication, a lock, employment approval or proof of current access.

A dedicated managed server signing key and safe verification/rotation configuration are implementation prerequisites, not provisioned by this document. Do not reuse API consumer tokens, Firebase browser values or import-signing keys. No new IAM grant is implicit; missing configuration fails closed. Use a reviewed keyed-signature implementation with strict algorithm/key-ID/audience checks and constant-time comparison. Keep tokens out of URLs, logs, repository artifacts and exported drafts. Do not enable the writer until key-management and route-denial tests pass.

The client shows expiry and invalidates confirmation whenever intent changes. The server verifies signed issue/expiry times for a previously uncommitted operation; client clocks/timestamps cannot extend validity. A command admitted before expiry can still be in flight after the display expires: expiry alone never proves that it did not commit. Changed membership, source documents, names used in copies, eligibility, parent hierarchy, relevant requests or linked-account state require a new preview, not silent rebase. No browser-loaded fallback may enable confirmation.

## 6. Commit and concurrent changes

Commit accepts a prepared UUID operation ID, exact normalized intent and review envelope; no mutation list. Reauthenticate, validate bounded shape/signature, then use a **read-write** transaction. Read the actor mapping, operation receipt, all bounded predicate queries, subject/counterparties and affected documents before staging writes. Check terminal receipt replay first after current authority and command-identity validation; for a prepared operation, enforce envelope expiry, regenerate the complete plan and compare its signed preconditions/hash. Commit must not create a missing preparation implicitly.

Recompute current dependency/membership and absence sets, not just listed records. Detect a newly linked User, new District-owned role, inserted/moved retail member, added/reviewed Pending request, deleted/recreated source or direct edit without an application-version bump. Compare native update times and explicit presence in addition to versions. On SDK transaction retry, recompute and compare with the **original confirmed** plan; never approve a new one automatically. Prove insertion/absence/query concurrency with the actual server SDK/emulator or isolated non-production integration tests before enabling the writer; a serialized in-memory fixture alone is insufficient evidence.

Final-state invariants: retained/new role eligibility and lifecycle; no effective leadership left on an inactivated subject; valid owner/Region membership for new/replacement grants and consistent District-derived copies; explicit removal-only treatment of retired/invalid-parent source ownership; preserved unrelated array members; no newly invalid workplace links; all linked-account inactivation blockers absent. Merge only allowlisted fields into current saved records. Preserve Person contacts/names/title/department, Location address/hours/notices/temporary closures, unrelated metadata, IDs and historical attribution. Update `status`/`activeStatus` consistently when explicitly inactivating; preserve lifecycle representation on `keep`. Inactivation preserves historical controlled-position IDs unless the administrator explicitly changes that selection.

Exact business field allowlist: Person `positionIds`, explicit `status`/`activeStatus`, `primaryLocationId`, `supportedLocationIds`; District `districtManagerId`; Location allowed leadership IDs and their existing derived name arrays/scalars, plus `storeManagerPhone`/`storeManagerPhonePrivacy` only as derived copies for a changed SM. Server version/timestamp fields are additional metadata, not caller inputs. Reuse and test the current contact/privacy resolver for SM copies; clear an outgoing SM's copy on vacancy, never carry their phone/privacy into a replacement, infer a Person email or widen visibility. Read source contact only internally when needed; preview says that a compatibility copy changes without exposing the raw contact. No Location Region/District membership, ownership-adoption, account, position-catalog or email fields are writable here.

Stage the subject/owner/derived-copy changes, deterministic audit and committed receipt in that one transaction. Every changed business record increments its version once, with one server timestamp. Do not version unrelated read-only records. Final-state graph validation must cover the combined result, not validate an invalid intermediate promotion/handover. No emails, provider calls or client state mutation inside a retried transaction. V1 sends no automatic notifications; audit is not proof that a message was delivered.

Firestore documents read-before-write, retry behavior and all-or-none application in its [transaction guidance](https://docs.cloud.google.com/firestore/native/docs/manage-data/transactions); [contention guidance](https://docs.cloud.google.com/firestore/native/docs/transaction-data-contention) describes server concurrency. These support the transaction approach, not a claim that this unimplemented command or its predicate coverage has been tested. Do not change database concurrency mode as a shortcut.

## 7. Durable outcome, replay and cancellation

Receipt key: deterministic actor-UID-plus-operation-UUID namespace in a dedicated internal collection, derived by the server, never chosen by a body `actorId`. Bind schema/audience, subject, normalized intent hash and exact review-envelope hash; no raw token or intent is persisted in the receipt. A different actor cannot retrieve or seal this receipt, even knowing its UUID. Reject same-actor UUID reuse with different content even if the requested final state happens to match. Separate actors' UUID namespaces are not a global deduplication guarantee; current-state transaction preconditions arbitrate conflicting staffing changes.

Before any request, persist a protected, actor-namespaced recovery marker with operation UUID, subject ID and immutable command digest, no contacts/reason/raw intent/token. Storage failure disables submission. The explicit `prepare` request verifies fresh authority/signature/expiry and writes only minimal `prepared` receipt metadata and signed plan identity, not staffing or access. It is distinct from the read-only preview. Only after preparation is confirmed may the client dispatch commit. Receipt identity fields never change; state transitions are `absent → prepared → committed/cancelled`, or `absent → cancelled` to seal a late preparation. Terminal states are immutable.

Status/recovery-list use fresh authority and server-derived actor namespace, not possession of the original token. On restart, the marker and a bounded own-`prepared` recovery query must be reconciled before a new command for the subject is enabled. Query limit: 50+1; overflow fails closed and requires administrative reconciliation, not silent truncation. This query is a recovery aid, not an exclusive staffing lock. A server preparation with no locally retained intent/envelope may be inspected/cancelled but not reconstructed into a commit from names or guesses. Signed-out/different-user sessions cannot read another actor's markers/receipts; clear protected client state on sign-out, then recover the same actor's server preparations after authorized sign-in. Audit receipt reads/retention according to the existing internal-data policy; never publish operation lists.

Store only minimal outcome metadata: state, operation/actor/subject IDs, immutable command digest, original server times, changed IDs/new versions and deterministic audit ID. No raw contacts, signing secret or before/after document dumps. A prepared receipt is not proof of a staffing change, and an expired preparation is not automatically a confirmed cancellation.

Commit business writes, audit and terminal receipt state atomically. Two identical concurrent submissions produce one effect/audit and a replayed original receipt; a previously committed receipt remains recoverable after preview expiry or later staffing changes. A retried commit still verifies its original signature but does not reject an already committed receipt solely for expiry; minimal status recovery requires current actor authority and matching marker identity, not a stored token. Revoked/downgraded sessions do not gain receipt access.

On network loss/timeout/5xx or malformed success from prepare/commit, retain the recovery marker and any in-memory immutable intent/envelope and show **Outcome unknown**, not success or failure. Disable edits/new submission IDs. Explicit status/retry uses the same command identity. A receipt replay says the original operation committed, not that its saved values remain current: refresh saved Directory state instead of merging old receipt data over newer records.

Missing receipt is not proof of no in-flight prepare. Cancellation uses fresh authority, the server-derived actor namespace and exact recovery-marker command identity; it needs no original token and cannot authorize staffing writes. It transactionally seals an absent/prepared operation with a cancelled receipt and deterministic audit, or returns the existing committed outcome without undoing it. A late prepare must compare identity and reject the cancellation tombstone. Commit and cancel race on the same receipt key: one outcome wins, never partial business changes. Expiry permits recovery/sealing only, not a new staffing commit. Only confirmed cancellation enables an editable draft and new preview/operation ID.

If permission is lost, keep the local result unknown and request authorized administrative reconciliation; do not broaden access or pretend the action was cancelled. Status/cancel return only the authenticated actor's minimal matching receipt. No token/intent export into URLs or logs. Protected markers, own-preparation recovery across reload/sign-out/sign-in, and late prepare/commit cancellation races are prerequisites to enabling v1, not a warning-only deferral. Never discard receipt/tombstone identity with TTL or prune replay protection without a separately reviewed retention contract.

Validation/known stale before admission returns a structured no-write error. Infrastructure failures after dispatch are unknown until receipt reconciliation. UI copy: `Review required`, `Preview ready`, `Saving`, `Saved`, `Outcome unknown`, `Cancellation confirmed`, `Already saved`; distinguish 400 invalid intent, 401/403 auth, 409 conflict/cancelled/reused identity, 413 application capacity, 429 throttled, 503 unavailable. None authorizes a new operation while a dispatched previous outcome remains unresolved.

## 8. User experience and accessibility

Keep the current Person disclosure as an entry point, not another always-open admin form. Future command opens one bounded, accessible dialog: choose change → explicitly retain/select positions → review each ownership decision → workplace/request/account review → before/after confirmation → saved receipt or recovery. Never preselect replacement/vacancy, drop an old role, or transform a job title into a new assignment.

Show District decisions once with affected-store counts and expandable derived effects; Location-owned slots remain separate. Display current/retired/missing/non-retail context, immutable IDs and human names together. Require an explicit inactivation checkbox and clear account blockers; do not present `Save` as complete external offboarding. Preserve entered intent on known failure, focus errors, disable duplicate submission, support keyboard/mobile and restore focus on close. Escape/backdrop may close only when not saving/unknown; block dismissing an uncertain operation without explaining recovery. No hidden automatic retry that can create another write.

## 9. Implementation sequence and exit evidence

1. **Pure dry-run planner, no routes or writes.** Schema/normalization, scoped mutations, full dependency/provenance and deterministic plan hash. Synthetic fixture matrix and frozen-source tests; no new live inventory dump.
2. **Command preview and signing configuration.** Read-only server planner adapter, current authority, native preconditions, capacity/expiry/denial/metadata projection. Explicitly separate from the already deployed PR49 informational read. Writer still disabled/unavailable.
3. **Prepare/atomic commit/receipt/status/cancel/recovery list.** Server-derived allowlist and final-state invariants, actual query-concurrency evidence, protected client markers and reload recovery, idempotent/recovery/permission tests. No account/provider capability. Preserve existing direct-write safeguards and public consumer contracts.
4. **Guided UI and release.** Synthetic accessibility/mobile/stale/timeout/restart UX, targeted build/route/docs guards and no-traffic release. Real staffing choices and any access work remain owner actions; consumer acceptance and restoration stay separate.

Required fixtures include: retain SM+add DM without assignment; vacant District assignment; multi-District departure; array-member replacement preserving others/order; retired/zero-store District and retired/non-retail Locations; legacy ownership/unclassified type/missing or inactive counterpart; all linked User states; new account/membership/reference insertion; unchanged and unversioned changes; lifecycle/position conflict; stale signed plan/name/parent; expired/tampered/wrong-audience/actor token; duplicate submit/content reuse; receipt replay after expiry; lost response; commit/cancel race and late arrival; capacity with zero writes; permissions lost between preview/commit/recovery; no external access/contact/operating-state mutation. No actual personnel example is an authorized live test.

## 10. Existing-validator compatibility and rollout gate

`server/districtLeadership.ts` currently requires one District plus exactly its member stores, rejects unrelated writes, and checks copies/membership/version/audit limits. `server/personPositionValidation.ts` and `server/firestoreDirectory.ts` guard final eligibility, Person lifecycle and User links. Therefore the generic commit cannot safely become a combined transition just by appending Person writes, making several commits, passing a bypass flag or weakening that District guard.

Extract/reuse pure final-state invariants where appropriate, while retaining the current District-only route's exact shape and permission tests. Add a distinct server-derived transition validator for the new complete atomic intent. Inventory every alternate writer before refactoring; existing direct edits, requests, import/export and compatibility readers must retain their protections. Preserve read-only PR49 behavior and schemas. Account/provider work, Region/acting cutover and larger batching require their own reviewed contracts.

Release gates: plan review → pure planner evidence → server/concurrency/recovery evidence → UI/accessibility/security review → compatible no-traffic release → separately authorized real acceptance. Contract publication is only the first gate. Code rollback and data recovery are distinct; never replay old full documents or reset collections to reverse a staffing change. Forward repair must respect current versions and later legitimate activity.
